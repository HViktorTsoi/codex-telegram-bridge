# Telegram ↔ Codex bridge

用一个 Telegram Bot 控制本机 Codex 会话，支持绑定已有会话或新建会话。绑定已有会话时保留原历史、模型和权限设置。这是通过 Codex app-server 工作的 Python 桥接程序。

## 让其他 agent 配置

可以把仓库地址和下列文字发给目标机器上的 agent。私有仓库需要先为该机器或 agent 使用的 GitHub 账号配置读取权限；Bot Token、Telegram 用户 ID 和实际会话绑定不在仓库里，需要在目标机器上配置。环境要求见下方“环境”一节。

```text
请部署 https://github.com/HViktorTsoi/codex-telegram-bridge，使用 v0.11.46 或更新的稳定版本。

先阅读 README.md、DEPLOYMENT.md 和 TOPICS.md，检查目标机器的 Python、tmux 和 Codex 服务。
复用本机已有 Codex app-server，列出并核对我要绑定的原 session；绑定时保持原 thread ID，不新建或 fork。
只有我明确选择 /sessions 的“新建会话”并确认时，才调用 thread/start；新会话使用本机默认模型和权限，创建本身不调用模型生成。
总览、Inbox 和派单只管理本机会话，不配置任何跨机器同步或路由。
在 All 回复本机已绑定话题中的消息时，直接投递到该话题，不再选择会话，只把新内容交给 Codex；话题内部回复继续附带引用原文。All 中其他普通消息先暂存，点击接收会话后直接投递；未选择时不发送，也不自动转给默认或最近会话。明确 @别名、/to 和系统指令沿用原流程。
使用独立 Bot 和私有配置目录，避免与已有实例争用同一个 Token；将访问策略设为仅允许本人 Telegram 用户 ID。
按需引导我开启 BotFather Threaded Mode；多会话模式应创建真实 Telegram 话题并保存返回的 topic ID，替换示例里的占位值。
在 BotFather 开启 Disallow users to create new threads，保留 Threaded Mode，让管理命令能留在主对话而不会被客户端自动建话题。
安装依赖并运行测试，再启动对应实例；manage.py 只管理默认实例，独立状态目录需使用 bridge.py 或 topics_bridge.py 的 run --state-dir 入口，不要误操作已有实例。
升级到包含 Footer 预览的版本时，先在实际运行桥接的 Python 环境重新安装 requirements.txt；新增 markdown-it-py 依赖必须在服务重启前就绪。
验证 /status 中的原 thread ID、Markdown 和图片输入；多会话模式还需验证 /sessions 和各话题的消息归属。
话题模式可使用 /skills 查询当前会话工作目录下可用的本机技能；All 中先选择会话。选择技能并回复文字任务后才运行模型，列表查询不调用模型。
在会话话题输入 /files 或点击状态栏的“📎 文件”，分页查看该原会话中 Codex 已回传的输出文件，点选后在当前话题重发；列表与重发不调用模型，不扫描项目目录。
按需启用 native_mirror，将本机 Codex 客户端新消息和回复同步到对应话题，不补发启用前的历史。
话题模式统一采用推荐呈现：在 config.json 顶层明确设置 notification_mode: completion、preview_style: status-bar、status_card_pin: false；核对 targets 中的同名覆盖，统一启用时删除旧覆盖或改为相同值，不修改会话绑定。
中途公开回复在同一条普通消息中累计更新，下方附两行持久按钮状态栏；任务运行时提供“⏹ 停止当前任务”，确认回到原话题，不调用模型。成功结束后先静音发送合并过程，再单独发送最终回复，仅最终回复末段正常通知；不另加成功完成文案。
新话题实例省略这些字段时采用上述默认值；升级已有实例仍需检查私有配置和已准备的发送计划，按 DEPLOYMENT.md 的迁移步骤明确设置并核验 health.json 中每个目标的实际模式。兼容显示模式只在用户明确选择时启用，不作为新部署方案。
中途正文默认 normal；如需无引用边框的小号淡色段落，可另设 preview_body_style: footer，并先核验客户端显示。此项不影响累计预览、状态栏、最终回复及通知规则。
缺少必要配置时再向我索取；Bot Token 只保存在目标机器私有凭据文件中，不提交到 GitHub。
```

目前支持的能力见下方“功能”。公开回复中的明确本机图片及文件下载链接可自动回传为 Telegram 附件。

## 功能

- 输入框下方提供会话、任务、停止三个常用按钮，单排显示并跟随客户端主题配色；`/keyboard` 可重新显示。
- 文字、图片、文件、相册、位置、联系人和投票输入。
- 会话话题内的 Telegram 引用回复附带易读的原消息正文和选中片段，帮助 Codex 理解“改这里”等指代。
- Codex 回复中的明确本机图片链接会上传为真实 Telegram 图片，支持 PNG、JPEG、WebP、GIF，适用于二维码、截图和图表；不依赖 `/format rich`。
- 明确本机下载链接支持 `.cmd` 脚本、PDF、Office、ZIP、APK、文本等常见文件，每个文件上限 20 MB，使用当前 Bot 回传到原话题。
- `/files` 和状态栏的「📎 文件」按话题展示 Codex 已回传的输出文件，分页、刷新并按需重发；不调用模型，不混入其他会话的文件。
- 一个私聊内用不同话题连接不同 Codex 会话。
- All 回复直达：回复本机已绑定话题中的消息，直接把新内容发到对应会话，不传引用原文；其他普通文字、图片、文件及相册仍先选择本机会话，未选择时不调用模型。
- `/sessions` 按钮流程：按名称和工作目录查看本机会话 → 选择 → 核对完整 ID → 确认绑定到新话题。
- 会话选择按最近实际使用排序；已绑定会话可用“修改名称”或 `/rename` 同步修改 Codex 会话名和 Telegram 话题名。
- `/sessions` →“新建会话”：按钮浏览本机文件夹、输入路径或新建文件夹，填写名称并确认后创建空 Codex 会话并连接新话题。
- `/skills`：按当前会话目录分页查看本机技能，选择技能并回复指定文字任务提示后交给原会话执行；All 中先选择目标。
- 已绑定会话可通过按钮重新创建话题，恢复删除后的入口。
- 话题模式默认在累计正文下附两行持久按钮状态栏，显示用时、等待、完成、停止和断连状态；兼容逐条发送模式也可显式启用独立工作状态消息。
- 话题模式默认仅在任务结束时通知：中途公开回复按条用空行及细分隔线累计预览，每约 15 秒更新同一条普通消息；成功后过程合并静音发送，Codex 最终回复独立发送并正常通知，图片与文件单独发送。
- 持久状态栏可直接点击“⏹ 停止当前任务”，仅停止这条预览绑定的运行任务；准备阶段提供“⏹ 取消待处理”，取消此前尚未投递的消息。`/stop` 使用独立控制入口，断连时也会取消尚未提交的消息并在原话题确认；历史按钮不会改停后续任务。
- 可选本机客户端消息同步：复制客户端的新输入和 Codex 回复到绑定话题，避免重复回显 Telegram 消息。
- `/tasks` 本机会话进度、`/inbox` 待处理事项、`@别名` 和 `/to` 本机派单。
- `/usage`：启用 All 中的 Codex 额度卡片，显示本机账户接口提供的使用窗口、剩余比例及重置时间，原地更新并静音置顶；不调用模型。
- 可选同 Bot 双会话群连通试验：群内点名专用命令，验证本机 CAD 与 Telegram Manager 的两句短确认接力。
- 话题模式的全局菜单和派单汇总显示在主对话，会话参数、停止等指令的回复发回输入所在对话。
- Codex 回复默认使用 Telegram Rich Markdown 排版，支持标题、表格、代码块和公式；可按会话切换纯文本。
- `/model`、`/effort` 查询和修改对应会话的参数；`/status` 核对绑定；`/stop` 停止对应会话的任务。
- 持久化收发队列、重复更新去重、按原目标恢复任务，未确认的输入不盲目重复执行。

默认每个 Bot 只接受配置的白名单用户的私聊。显式启用群连通试验后，只额外处理该用户在群里发送的专用测试命令，普通群消息不会转给模型。同一个 Token 只能运行一个更新接收器。

## 环境

- Linux、Python 3.10 或更新版本、tmux。
- 可访问的 Codex app-server Unix socket，且该服务能读取目标已有会话。
- Telegram Bot Token、本人 Telegram 用户 ID。

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m unittest discover -v
```

自动测试使用模拟 Telegram 和本机临时 socket，不需要真实 Token 或 Codex 登录。

升级已有实例时，使用该实例实际运行的 Python 解释器先安装 `requirements.txt`，再重启；Footer 预览新增 `markdown-it-py` 依赖。仅更新代码而不更新运行环境的依赖，不能视为完成升级。

## 配置

代码和每台机器的配置分开保存：

| 内容 | 默认位置 |
|---|---|
| 桥接配置、SQLite、日志、健康状态 | `~/.local/state/codex-telegram/` |
| Bot 凭据、访问白名单 | `~/.claude/channels/telegram/` |
| Codex socket 示例 | `~/.codex/app-server-control/app-server-control.sock` |

socket 路径应指向实际使用的已有服务；使用另一个新服务不等于接入桌面上正在使用的会话。配置中的路径需要填写为本机绝对路径。

多会话和本文推荐呈现使用话题模式，优先参考 [config.topics.example.json](config.topics.example.json)，并结合 [.env.example](.env.example) 和 [access.example.json](access.example.json) 创建私有配置。只需旧式单会话连接时才使用 [config.single.example.json](config.single.example.json)；它不提供话题模式的累计完成投递和按钮状态栏。Token、owner ID、socket 路径、原会话 ID 和话题 ID 都需要替换；核对完成后将 `setup_required` 改为 `false`。目录权限使用 `700`，凭据和状态文件使用 `600`。

绑定已有会话时应先用 `thread/read` 核对标题、ID 和历史，再用 `thread/resume` 恢复同一个 ID。程序不以 `thread/start` 或 `thread/fork` 作为绑定失败后的替代方案。

### 多会话话题模式

1. 在 BotFather 为该 Bot 开启 Threaded Mode / Topics，并开启 **Disallow users to create new threads**。
2. 将原会话绑定到一个 Telegram 私聊话题，参考 [config.topics.example.json](config.topics.example.json)。
3. 启动后发送 `/sessions`，点击“添加会话”绑定已有会话，或点击“新建会话”创建全新会话；无需重启。
4. 已有会话若尚未出现在列表中，点击“重新加载”；尚未持久化的电脑端草稿可能需要先发送首条消息。

`/sessions` 首页逐项显示已绑定会话的名称和工作目录。“添加会话”首先列出本机现有会话涉及的所有工作目录，每个目录按钮显示路径和会话数量；选中目录后，才展示其中的 sessions。目录列表超过 12 项时可翻页，使用“返回目录列表”可重新选择。会话页面顶部只显示一次路径，下方只列出该目录的会话名称按钮；也可用“上个目录／下个目录”快速切换。目录未提供时单独归组，较长路径保留首尾。此操作只读取本机会话元数据，不调用模型生成。

`/sessions` 首页、All 的接收会话选择、`/to` 和 `/rename` 的选择列表按最近使用在前排序。“添加会话”中的目录按其中最近使用的会话排序，同目录内也按最近使用排序；没有使用记录时保留原生列表的最近更新顺序。使用记录按原 Codex 会话 ID 持久保存，包括已接收的话题消息及会话指令、已选择投递的 All 消息、已投递的派单和完成的改名。单纯点开话题的浏览时间无法从 Bot API 获取；仅查看菜单、取消选择、机器人回复及状态刷新不会更新顺序，也不将电脑端单独使用时间当作 Telegram 访问记录。

同一目录超过 12 个会话时在该目录内分页；选择会话后返回列表会保留当前目录和页码。打开列表时读取完整的原生分页结果再分组；目录快照持久化，切换目录和翻页使用同一份快照，避免其他会话更新导致列表跳动。点击“重新加载”更新数据并保留当前目录；长时间未操作导致列表过期时可重新加载。

“新建会话”流程从本机用户主目录开始，点击文件夹进入、点击“上级目录”返回，也可显示点号目录。子目录每页 10 项。“输入路径”支持绝对路径、`~/` 和相对于当前目录的路径；“新建文件夹”只创建当前目录下的一层，支持中文和空格，不覆盖同名文件或文件夹。新建后进入该文件夹，仍需点击“使用当前目录”确认工作目录。

路径、文件夹名和会话名称通过 Telegram **回复输入提示**填写，手机通常会自动进入回复状态；若没有，请长按提示选择“回复”。只有回复指定提示的文字才进入该流程，普通消息继续正常聊天。回复提示 `/cancel` 或点击“取消”可取消；已经新建的文件夹会保留。普通选择和输入提示有效期为 15 分钟。

提交路径、文件夹名或会话名称后，更新后的目录或确认卡片会作为新消息显示在这条输入下方。旧卡片按钮会失效，界面上的旧按钮也会尝试清除。通过按钮浏览目录时继续原地更新。

填写名称后展示主机、目录和名称，点击“确认新建并连接”才调用 `thread/start`，再用 `thread/name/set` 命名并绑定返回的同一个 ID。新会话继承本机 Codex 默认模型和权限，不复制原会话的历史；直到你在新话题发送消息才调用模型生成。接口依据 [Codex 官方 app-server 文档](https://learn.chatgpt.com/docs/app-server)，本机 app-server 需支持这两个方法。已有会话的绑定和修复仍不会调用 `thread/start` 或 `thread/fork`。

创建记录持久化到私有 SQLite：重复点击不会重复创建；创建成功后命名或绑定失败，可在 `/sessions` 首页点击“继续处理”沿用已记录的新会话 ID。若 `thread/start` 或 `createForumTopic` 的返回结果丢失，会提示先核对已有会话或话题，不自动重建。

已填名称、尚未确认的草稿在有效期内也会出现在 `/sessions` 首页的“继续处理”入口。确认卡片发送失败时，可手动打开该入口恢复卡片，名称和目录保留；恢复卡片不会重放先前的文字输入，也不会自动创建会话或话题。

如果 Telegram 明确返回 `BOT_TOPIC_WRONG_HOME`，桥接会提示话题服务暂不可用，保留已创建的 Codex 会话，并提供“重试连接”入口。此错误触发同一 Bot 与私聊 5 分钟的持久冷却；期间不调用话题创建接口，新建向导也不会先生成另一个空会话。冷却结束后手动重试会继续同一个原生会话。客户端出现“话题已创建”的服务记录不代表该话题可用，桥接不会据此猜测话题 ID 或绑定。Telegram 官方仓库的[相关故障报告](https://github.com/tdlib/telegram-bot-api/issues/944)记录了这类现象；本地处理不能替代 Telegram 服务恢复。其他明确拒绝和未知结果仍按原规则处理。

### 修改会话名称

发送 `/sessions` → 选择已绑定会话 →“修改名称”，回复名称输入提示，再点击“确认改名”。也可在对应话题输入 `/rename`，或 `/rename 新名称`；在 All 输入该命令会先选择目标，不默认使用最近会话。名称输入、核对和结果面板统一显示在 All；只有回复指定名称提示的文字进入改名流程，回复 `/cancel` 或点击“取消”可退出。

确认后依次更新原 Codex 会话名、同一个 Telegram 话题名和本机绑定记录。会话 ID、话题 ID、历史、正在执行的任务、模型和权限保持原值；既有显式别名和 target key 继续可用。改名只使用元数据接口，不调用模型生成。名称须为非空单行，最多 90 个 UTF-16 单元（部分表情占两个），不能与本机其他已绑定会话重名。

改名进度持久保存；Codex 已改名而 Telegram 暂时同步失败时，可在 `/sessions` 首页或该会话的“修改名称”入口点击“继续同步名称”，沿用原会话与话题继续处理。绑定或名称在同步中被其他操作修改时会停止并提示核对，不改投其他会话；话题已失效时先修复绑定。

`root_target` 继续提供原会话及主对话系统指令的上下文；All 回复可直接使用被回复消息的绑定话题，其他普通内容在选择目标后投递。话题模式、恢复策略和完整配置说明见 [TOPICS.md](TOPICS.md)。

上述 BotFather 开关阻止 Telegram 客户端在主窗口发送 `/tasks`、`/sessions` 等消息时先自动创建话题。可用 `getMe` 验证 `has_topics_enabled=true`、`allows_users_to_create_topics=false`；此开关需要 Bot 所有者在 BotFather 设置，Bot Token 无法修改。它同时禁止用户手动新建、编辑和删除话题，桥接仍可通过 `/sessions` 创建和重建绑定话题。参见 [Telegram 官方说明](https://core.telegram.org/api/forum#bot-forums)。

话题模式中，`/sessions`、`/tasks`、`/inbox`、`/usage`、`/to`、`/aliases`、`/help`、`/start` 等全局菜单及派单汇总发送到主对话；旧话题里的管理菜单按钮会在下一次操作时转到主对话。`/status`、`/model`、`/effort`、`/format`、`/stop` 作用于输入所在话题对应的原 Codex 会话，查询结果、确认和错误提示均发回输入所在对话；在主对话输入则回复主对话。未知命令及未绑定话题中的会话指令错误也回复原处，未绑定会话不会改投默认目标。发送层只显示正文，不自动添加 `〔会话标题〕` 前缀。普通对话、图片和状态提示继续使用原话题；已有发信队列保留原来保存的位置。

`/skills` 菜单、任务输入提示和操作反馈留在输入所在对话，Codex 回复仍在目标话题。已绑定话题直接使用该会话；All 先选择本机已绑定会话，不默认选择 Manager 或最近会话，选择列表按最近使用排序。未绑定话题不会改投其他会话。

直接输入 `/sessions` 使用独立的菜单处理通道，首页读取本机已保存的目录信息，无需等待正在执行的任务或较早的目录查询、绑定、改名操作。尚无缓存的目录会显示待同步，后续原生元数据读取会补充；缓存只用于显示，实际绑定与重建仍重新核对原生会话身份。

### 底部常用按钮

话题模式默认启用输入框下方的自定义回复键盘，一排显示「会话／任务／停止」。按钮采用 Telegram 客户端默认主题配色；具体外观与展开状态由客户端决定。未展开时可点输入框旁的键盘图标，或发送 `/keyboard` 重新显示。填写新建、改名、技能及问题提示后，如键盘被客户端替换，也可用该命令恢复。

会话、任务、待处理和帮助沿用 All 管理入口；模型、强度、技能和停止沿用当前对话对应的原命令。建议先进入目标话题再点模型、强度或停止：话题内作用于该原 Codex 会话；All 中模型、强度和停止使用原 Manager 根会话，技能菜单会先选择目标。菜单查询本身不运行模型，停止只请求中断目标任务。

底部按钮与消息中的状态栏、停止和选项按钮同时保留。首次启用只在 All 静音发送一条安装消息，正常重启不重复发送；保留该消息，删除它可能清掉客户端键盘。`/keyboard` 明确请求重新发送安装消息。普通文字键盘按钮实际发送其标签，因此手动输入完全相同的带表情标签也会作为快捷指令；附件说明、转发文字和指定输入提示的回复保留原内容。可在本机配置中设置 `"quick_keyboard": false` 关闭该入口。

### All 防误发

在 All 回复某个本机已绑定话题中的消息时，桥接直接把你新写的文字或新发的附件加入对应会话，不再展示会话选择或确认页面。被回复消息只用于确定目标，原文和选中片段不会交给 Codex，也不会附在话题回显中。在话题内部回复时，仍按原规则附带引用原文。

All 中其他普通文字或附件仍展示消息预览和本机已绑定会话的选择按钮；点击一个会话后立即投递，不再显示第二次确认页面。选择前可点击“取消”，每条消息分别选择目标，不沿用上次选择，也不自动投给 Manager 或最近活跃会话。无法确认回复所属话题、跨聊天引用、话题已删除、绑定变化或相册目标冲突时，内容保留在待发送流程中，供你重新选择。

投递时，新文字或附件说明文字也会以“📩 你在 All 说：”同步到目标 Telegram 话题。Rich 模式下，标题保持普通文字，仅用户正文显示为引用块；`status-bar`、`status-draft` 的普通消息预览及完成后的过程部分均保留此样式，技能菜单中从 All 提交的文字任务也使用同样的回显。引用样式只改变显示，Markdown 符号、HTML 与链接按原文呈现，纯文本降级仍保留新正文。回显使用持久化发送队列，重复更新、重复点击及重启恢复不会重复入队，也不会额外调用模型。启用仅完成时通知后，完成时的原文回显静音发送。此处只复制文字，不复制图片或文件本体到 Telegram 话题；用户输入中的本机链接不会因回显而触发附件上传，附件仍按原流程交给 Codex。取消或仍待选择时不显示，不补发之前已完成的历史记录。

相册在同组附件连续 2 秒没有新增后统一处理：首条带有明确话题回复、其余成员未引用时，可一起直接投递；不同成员指向不同话题或存在无效引用时，仍需选择目标。普通相册展示一个选择入口，选择前新到的附件会使旧选择按钮失效。投递后才到达的后续附件另外暂存，不自动沿用先前目标。原文字和附件保留，目标未确定前不下载附件、不调用 Codex 模型。

暂存与投递记录持久化，重启后仍可处理；通过 `/sessions` →“待发送”找回未发内容。目标绑定在选择、投递和实际调用模型前都会核对，绑定变化时不自动改投。升级前已暂存的内容不会自动发送：有效旧选择按钮首次点击只刷新成新列表，再选择目标才会发送；已显示的旧“确认发送”按钮仍可完成原投递。已有话题内的普通聊天直接进入原会话；斜杠系统指令、明确的文字 `@别名`、`/to` 和既有指定输入提示回复沿用原流程。会话绑定、新建、改名和派单等其他流程的确认保持不变。附件 caption 中的 `/stop`、`@别名` 等只作为附件文字，不执行指令。

`All` 的位置由 Telegram 客户端控制，插件不能在它左侧插入空白标签；防误发流程使用 All 内的普通按钮，不新建空白话题。

### 图片与文件回传

让 Codex 在回复中使用 `![说明](/本机绝对路径/图片.png)`，带空格的路径可写成 `![说明](</本机路径/图片.png>)`。指向受支持图片的普通本地文件链接也会上传。单图上限 20 MB；超过 Telegram 照片限制的图片、GIF 或被明确拒绝为照片的图片会按原文件发送。

其他文件使用明确下载链接，例如 `[下载启动脚本](/本机绝对路径/start.cmd)` 或 `[下载文档](</本机路径/报告.pdf>)`。支持 `.cmd`、PDF、Office、ZIP、文本等常见文件，每个上限 20 MB。仅处理公开回复中的明确绝对路径链接；裸路径、相对路径、远端 URL、代码示例、用户输入、源码引用和凭据文件不会触发本机上传。

如果最终回复明确表示“已附上图片”等，却没有图片链接，桥接会补上该轮最后一张 `imageView` 图片；不会因为 Codex 内部查看截图就直接发送，也不会从其他轮次取图。多图请逐一使用明确图片链接。桌面端回复同步沿用相同规则；用户在桌面输入的图片仍只显示附件提示。

图片先保存到对应会话私有目录的 `outgoing-images/`，其他文件保存到 `outgoing-files/`，再进入持久化发送队列，始终发送入队时的固定快照。照片上传使用 `sendPhoto`，文件发送使用 `sendDocument`；附件始终沿用接收本次任务的 Bot 与冻结的原话题，`/format plain` 也能收附件。结果不明或上传过程中重启时，附件标记为待核对并停止自动重发；429 限流按原快照延迟重试。格式化失败不会触发另一份上传。仅完成时通知模式下，附件先静音发送，成功完成后再发送静音的过程合并部分及独立最终回复，只有最终回复末段正常通知；启用后不补发历史回复。

桥接不向输入追加 Bot、话题来源或文件回传指令，也不替换成隐藏的模型提示。用户正文按原有文字、引用与附件流程传入。附件回传由桥接读取公开回复中的明确本机链接，并使用当前实例的 Telegram 客户端及持久化队列保存的接收账号与话题发送。两个 Bot 可以连接同一个原生 Manager，分别按本实例已记录的任务与话题处理回传，无需为此解绑或停用独立 Bot。

## 运行与命令

在代码目录中运行：

```sh
.venv/bin/python manage.py start
.venv/bin/python manage.py status
.venv/bin/python manage.py logs
.venv/bin/python manage.py stop
```

`manage.py` 根据 `config.json` 的 `mode` 选择单会话或话题模式。单会话首次启动可使用 `start --notify`；话题模式使用 `/sessions`。电脑、网络和 Codex 服务需要保持运行；当前没有配置开机自启。

| Telegram 命令 | 操作 |
|---|---|
| `/sessions` | 话题模式下打开会话列表、添加和重建入口 |
| `/rename`、`/rename <新名称>` | 话题模式下确认修改原 Codex 会话名，并同步 Telegram 话题名；All 中先选择目标 |
| `/tasks`、`/tasks all` | 查看本机已绑定会话，或包括未绑定会话的本机完整目录 |
| `/inbox` | 查看原生等待和最新回复中的待确认问题，回复、稍后处理或标记已处理 |
| `/usage` | 启用并显示 All 中的本机 Codex 额度卡片 |
| `/collab_test@Bot用户名` | 显式配置双会话群试验后，在当前群或话题启动一次短确认接力 |
| `/collab_status@Bot用户名`、`/collab_stop@Bot用户名` | 查询本话题的试验状态，或停止后续接力 |
| `/to`、`/to <别名> <任务>` | 按钮选择目标派单，或直接指定原会话 |
| `/aliases` | 查看可用的本机 `@别名` 派单名称 |
| `/skills`、`/skills <关键词>` | 话题模式下查询或筛选本机会话可用技能，选择技能并输入文字任务 |
| `/files` | 查看当前话题中 Codex 已回传的输出文件，点选后在原话题重发 |
| `/model`、`/model <ID>` | 查询或切换当前目标会话的模型 |
| `/effort`、`/effort <级别>` | 查询或修改当前目标会话的推理强度 |
| `/format`、`/format rich`、`/format plain` | 查询回复格式，或切换排版与纯文本 |
| `/status` | 显示主机、会话名称、完整 ID 和参数 |
| `/stop` | 停止当前目标会话的任务，并取消此前尚未投递的消息 |
| `/help` | 查看说明 |

参数命令调用 `thread/settings/update` 并回读确认，不启动模型生成。普通消息沿用原会话设置。原 Codex 客户端继续处理审批和其他交互请求。

### 会话文件记录

在已绑定的会话话题输入 `/files`，或点击持久状态栏、最终回复状态按钮中的「📎 文件」。列表只读取该原生会话中 Codex 已回传的文件快照，显示文件名、类型、大小和时间，支持分页和刷新。点选文件后，由当前 Bot 静音重发到当前话题。All 中的 `/files` 提示前往目标话题，不默认选取根会话或最近会话；底部仍保留会话、任务、停止三个按钮。

列表仅显示 Codex 已回传的输出文件，不显示用户上传或输入的附件。仅在项目目录生成却未交付的文件，不会自动出现在列表中。不会扫描项目目录，也不会把工具查看过的图片或截图当成交付文件。重复的文件记录会合并，同名但内容不同的回传文件保留为不同版本。快照缺失或校验失败时提示无法发送，不改用其他路径或 Bot。

浏览与重发均不启动模型。菜单、入口和发送操作固定本人账号、Bot、原生会话与话题；删除、重绑或重建话题后，旧按钮失效。发送结果不明时不会自动重发，检查话题后可刷新列表并明确再次点选。

### 双会话群连通试验

此入口先验证同一个 Bot 下、本机已有的 CAD 与 Telegram Manager 两个会话，不是跨 Bot 或跨机器路由。默认关闭；由部署 agent 在本机 `topics.sqlite` 的 `kv` 中设置 `group_collaboration_settings_v1`，包含 `enabled: true` 和两个 `participants`。每个参与者的 `key`、`thread_id`、`topic_id` 必须与现有本机绑定一致，`role` 按顺序为 `CAD`、`Telegram Manager`。其他机器不配置此项即保持关闭。

1. 用配置的本人 Telegram 账号创建私密测试群并加入该 Bot。普通群或已有群话题均可；仅需 Bot 能入群、发消息，不要求管理员权限，也不会自动创建群话题。
2. 在选定群或话题发送 `/collab_test@你的Bot用户名`。桥接从这条消息取得群与话题 ID，并固定本轮参与会话。隐私模式开启时，请保留命令中的 Bot 用户名。
3. 用 `/collab_status@你的Bot用户名` 查看状态，或用 `/collab_stop@你的Bot用户名` 停止后续接力；停止不会强行中断已经开始的会话任务。

每轮最多向模型投递两条短请求：CAD 先返回带本轮编号的一句确认，Telegram Manager 收到这句确认后回复一次，随后结束。参与会话忙碌时等待空闲再接续，每轮有效期十分钟；如果 Manager 正在处理配置本身，会在本轮工作结束后接续。只回传匹配本轮编号的确认，不共享历史、项目文件或其他输出，不新建 Codex 会话、不复制或改变原私聊话题绑定。重复更新、断线与未知发送结果不会自动产生重复投递或重复回包。

### Codex 额度卡片

在话题模式发送 `/usage`，启用并显示 All 中的单条额度卡片；也可在配置顶层设置 `"usage_card": true` 启用。显式命令的启用选择会持久保存，重启后沿用。默认关闭，新部署和升级不会自动给其他用户置顶卡片；输入框下方仍保留「会话／任务／停止」三个快捷按钮。

卡片不显示标题，直接以剩余额度的字符进度条与文字百分比开头，例如 `████████░░ 剩余 78%`；不显示已用比例、主机名称或单窗口的长标签。存在多个额度窗口时才使用 `5h`、`7天` 等短标签区分，重置时间和缓存新鲜度继续显示。“重置”行前缩进四格，缓存行仅显示新鲜度，不显示“额度查询”或“事件推送”来源标签。数据来自本机 Codex 账户接口，各本机会话共用同一份缓存，不逐会话请求，也不跨机器汇集。窗口或重置时间缺失时如实显示未知；倒计时结束不自行把额度重置为零或满额。

桥接只从本机根连接接收 `account/rateLimits/updated` 事件；连续 15 分钟没有新数据才用只读接口兜底查询。每分钟在本地重绘重置倒计时，不为倒计时额外请求 Codex；手动刷新受 60 秒硬冷却限制。卡片在同一条消息原地编辑并静音置顶，查询、显示和刷新均不调用模型。接口依据 [Codex 官方 app-server 文档](https://learn.chatgpt.com/docs/app-server)。

### 技能菜单

在已绑定话题发送 `/skills`，查看该 Codex 会话工作目录下可用的技能；在 All 发送时先选择目标会话。可用 `/skills <关键词>` 按名称和用途筛选。列表每页 8 项，支持翻页和刷新；点击技能查看用途、来源及启用状态，再点击“使用此技能”。相同名称但路径不同的技能保留为独立项；禁用技能可查看，不能发起任务。菜单不安装技能，也不修改启用设置。

选择技能后，使用 Telegram 的“回复”填写指定输入提示，例如“提取 PDF 中的表格”。只有这条明确的文字回复会提交技能任务；回复 `/cancel` 可取消，其他系统指令仍按原流程处理，普通未引用消息不会被输入提示接管。此入口先支持文字任务；图片、文件和相册请在对应话题使用现有附件流程，附件不会被菜单当成文字任务静默接收。

菜单通过 `thread/read` 取得原会话目录，再调用只读 `skills/list`；刷新会请求重新加载。列表、详情及选择操作均不调用模型。提交文字任务时重新核对会话绑定、目录、技能名称、路径和启用状态，再把用户原文与 `skill` 输入项一同交给原会话，不向正文追加路由或文件传输注解，不改模型、effort 或权限。All 中提交的任务原文会同步到所选话题；重复回复、按钮操作及重启恢复不会重复派单。接口说明见 [Codex App Server Skills](https://learn.chatgpt.com/docs/app-server#skills)。

### 引用上下文

在已绑定的 Telegram 话题内长按某条消息并选择“回复”，随后发送新要求。桥接会在本次输入后空行分段，以易读正文附加引用内容，明确区分新要求与被回复的材料。手动选中的片段优先显示，原消息正文随后供参考；两者相同时不重复。消息 ID、话题 ID 等元数据保留在内部记录中，不发送给模型。普通文字、富文本中的标题、表格和代码都可提取；相册重复的同一引用只附加一次。例如：

```text
把这句话翻译成英文

［引用内容］

> 需要翻译的原文。
```

在 All 发送的普通回复使用被回复消息所属话题确定目标，只提交新内容，不附加上述引用内容；无法确定目标时先选择会话。没有引用时，原消息和输入结构保持原样；命令仍按原规则处理，不因引用额外启动模型。新消息里的图片、文件和相册继续使用现有附件流程。话题内引用原文最多保留 12,000 字符，选中片段最多 4,000 字符，超长时标记截断；原文未随 Telegram 更新提供时明确标记不可用，不猜测或抓取历史。

被引用的附件只提供类型、文件名及说明，不自动重新下载；需要模型看原图或原文件时，请重新附上。引用只帮助理解内容，不改变当前话题对应的 Codex 会话；`@别名` 和 `/to <别名> <任务>` 仍以明确目标派单，同时保留引用。`/to` 按钮和 Inbox 的指定回复继续使用原绑定流程。

### 回复排版

默认将新的 Codex 正式回复通过 `sendRichMessage` 发送，使用 Telegram 的 Rich Markdown。菜单和其他控制回复使用普通文字；普通状态卡使用 Rich HTML 加粗，累计草稿可选纯文本或整块进度预览。客户端需要支持 Telegram Rich Messages。

在对应会话发送 `/format rich` 开启排版，`/format plain` 改为纯文本，`/format` 查看当前选择。选择按目标会话持久化，对之后生成的回复生效，不更改模型参数。

长回复按段发送；代码围栏会在分段处补齐，原始文字另行保留。服务端明确拒绝格式或不支持富文本接口时，发送同一段原文。话题不存在、权限、限流和送达结果不明的网络错误不会被当作格式错误降级。逐条发送模式保留旧队列的内容和分段；仅完成时通知模式在成功完成后分别合并尚未发送的过程和最终回复，失败或停止继续合并正文与相应说明；已经开始发送的分段保持固定。更新不会将已经投递的历史重新发送。

符合回传规则的本机图片和文件链接会先进入附件队列；其他本机链接在正文中显示为名称和路径，避免 Telegram 尝试读取本机路径而使整条回复退回纯文本。未上传的本机图片会明确标注“尚未上传”；公网链接和代码示例保留原样。格式化步骤只改写文本，文件读取与上传由独立附件队列处理。

### 仅任务结束时通知

话题模式的新实例默认使用累计预览与持久按钮状态栏。部署和统一迁移时，在私有 `config.json` 顶层明确合并以下三项：

```json
{
  "notification_mode": "completion",
  "preview_style": "status-bar",
  "status_card_pin": false
}
```

这只是需要合并的字段，不是完整配置文件；保留凭据、访问策略、原会话及话题绑定。单个 `targets` 项的同名设置优先于顶层；选择统一呈现后，应删除旧目标覆盖或改成相同值。既有实例的显式配置仍优先，旧任务的发送计划也可能保留原方式，不能仅凭升级代码判断所有目标已完成迁移。具体步骤和健康状态核验见 [部署文档](DEPLOYMENT.md#呈现配置与旧实例迁移)。单会话模式保持原行为。

普通任务消息写入接收队列后，独立预览流程会立即尝试显示“已收到，正在准备”，无需等待附件处理、Codex 启动请求返回、首条回复或历史读取。连接未就绪时显示等待连接，投递结果尚不明确时显示正在核对；可见时间仍取决于 Telegram 和网络。此流程覆盖话题消息、已选择目标的 All 消息及已投递的派单；系统指令、空消息、无权限输入和未选择目标的 All 消息不触发。向正在执行的任务补充要求时保留累计正文，取得真实任务 ID 后沿用同一预览。

`status-bar` 将累计公开正文和两行内联状态栏放在同一条普通消息中。收到任务后首次静音创建接收占位，后续每约 15 秒编辑同一消息；没有新正文时只编辑按钮栏位，不另发状态气泡。状态文字使用不可点击按钮；已确认真实任务运行时，第二行旁显示“⏹ 停止当前任务”。按钮停止这条预览对应的具体任务，核对白名单、Bot、话题、消息及任务身份后请求中断，确认回到原话题，不调用模型。接收占位及终态栏不显示停止按钮；旧按钮不能改停后续任务，重复操作、重启及结果不明时不会自动重复中断。

不同原始子消息之间使用空行与 `────────────` 分隔线；同一消息的内部切片直接拼接，避免在代码、表格或句子中加入额外空行。预览超过 3800 个 UTF-16 单元时显示最近部分并注明，完整原文和附件快照仍保留在持久化队列。状态栏随消息滚动，不固定悬浮在屏幕边缘。它使用普通消息及内联键盘，没有临时草稿的 30 秒期限；首次静音创建仍可能显示系统横幅。

只有原生任务明确进入 `completed`、`failed` 或 `interrupted`，且完整历史读取成功后，才释放正式输出。成功后分别发送过程合并部分与独立最终回复：优先选最后一条 `final_answer`，缺少阶段信息时取最后一条公开助手消息；没有过程时只发最终回复。过程和最终回复分别按每条最多 3800 个 UTF-16 单元分段，代码围栏在分段处补齐，完整原文保留。图片和文件单独静音发送，只有最终回复末段正常通知；失败和停止继续合并正文与相应说明，仍仅末段正常通知。

成功正文不再附加“✅ 本轮任务已完成”，最终回复末段保留持久终态按钮栏。取得最终发送的明确确认后，按持久保存的确切消息 ID 清理该轮预览。`final_answer` 中间项、等待输入或审批、断连及未知状态都不会被误当整轮完成。电脑端镜像使用相同规则，不补发旧已完成历史通知；主动系统指令仍可及时回复。

完成记录、固定目标和发送意图持久保存，重复事件及重启不重复生成提醒；发送结果不明时不自动重发。升级不会改写已发送历史，已经预制或尝试发送的旧计划继续按原有固定内容恢复。此功能只管理显示和投递时机，不额外调用模型，不改变会话、历史或参数。正常通知仍受 Telegram 静音及系统勿扰设置影响；静音发送保证无声音，不保证所有系统都不显示横幅。[通知参数说明](https://core.telegram.org/bots/api#sendmessage)

#### 可选中途正文样式

正文默认 `preview_body_style: "normal"`。在 `status-bar` 或 `status-draft` 模式下，可显式使用 `"quote"`，将 Rich 累计预览包在不折叠的引用块中，保留段落、代码、表格和嵌套引用；字体和背景由客户端主题决定。

也可使用 `"footer"`，让普通顶层 Markdown 段落显示为无引用边框的小号主题次要色，标题、列表、原有引用、代码块和表格保持正常结构。具体字号和颜色随客户端主题及文字大小设置；先在单个话题核验，再按需在顶层启用。顶层与目标设置均可用，目标优先。样式只改变中途预览，正式过程、最终回复、控制回复和持久原文保持原样；纯文本及格式降级时发送原文，更新代码不会自动启用 Footer。

#### 兼容显示模式

以下模式保留供明确选择的旧配置使用，不是新部署推荐值。它们不改变 15 秒刷新、固定路由、完整原文和仅完成时通知规则：

| `preview_style` | 中途显示 |
|---|---|
| `plain` | 状态和累计正文共用纯文本临时草稿；动画由客户端控制 |
| `block` | 状态和累计公开正文放在一个 Rich `thinking` 草稿区块中；不是隐藏推理 |
| `status-card` | 独立普通状态消息复用编辑，累计正文另用临时草稿；状态消息位置固定 |
| `status-draft` | 累计正文使用每轮创建一次后编辑的普通消息，两行状态另用底部临时草稿 |

临时草稿停止刷新约 30 秒后消失，切后台后也可能需要下一次刷新才恢复。`plain` 和 `block` 的预览不受支持时继续暂存正文，不另发普通进度消息；`status-card` 和 `status-draft` 的首次普通消息创建可能显示静音横幅。显式配置的旧样式继续保留；统一迁移应明确写入 `status-bar` 并核对目标覆盖。省略字段不会清空持久记录，也不会重排旧任务内容。参见 [草稿接口](https://core.telegram.org/bots/api#sendmessagedraft) 和 [流式预览说明](https://core.telegram.org/api/bots/ai)。

`status-draft` 会在确认有新的普通消息后，为状态草稿分配新的草稿 ID，尝试将状态放在最新内容之后；定时刷新和正文编辑复用原 ID。位置和 ID 在请求前持久保存，重启及重试不反复轮换；实际位置仍由客户端决定。

只有明确选择 `status-card` 时才考虑 `status_card_pin: true`；默认保持 `false`。它只尝试将该状态消息静音加入置顶列表，不改变其他置顶。Bot API 不能指定置顶栏只在某个话题显示，接口成功也不保证客户端位置；不能将置顶视为话题内固定悬浮状态条。[置顶接口](https://core.telegram.org/bots/api#pinchatmessage)

#### 显式逐条发送与旧状态卡

显式设置 `notification_mode: "all"` 会保留逐条发送方式；在此模式下，`activity_indicator: true` 可显示独立工作状态消息。它与推荐的 `completion` 加 `status-bar` 是不同的呈现选择，不应混作统一部署配置。

旧状态卡采用两行布局，首次静音创建，之后每约 15 秒刷新。`activity_position: "bottom"` 会在有新回复、图片或普通输入时先确认新的底部状态卡，再删除旧卡；没有新内容时只编辑，不会每 15 秒新发一张。设置 `"inline"` 则原地更新。换卡意图、旧卡清理及限流重试持久保存，结果不明时不重复创建；话题修复后旧卡不会改投其他话题，启用时不补发历史状态。它是普通消息，仍随聊天滚动。

### Codex 客户端消息同步

话题模式可在配置顶层设置 `"native_mirror": true`，或在单个目标上启用／关闭，单个目标优先。默认关闭。开启后首次观察会话时建立同步起点，不补发当时已有的消息；以后在 Codex 客户端发出的新输入与公开的 Codex 中间回复、最终回复会复制到对应 Telegram 话题。用户输入标注“🖥 你在 Codex 客户端说：”，由 Bot 代发；Rich 模式下整份输入回显使用引用块，在普通 Rich 消息预览和完成后的过程部分与 Codex 回复区分。输入原文、纯文本降级、附件判定与 All 回显遵循相同规则。使用 `preview_body_style: "footer"` 时，输入引用保持引用结构，普通过程段落才使用小号淡色；Codex 最终回复保持正常排版。普通会话操作继续使用同一个原 thread ID。

同步只读取本机原会话记录，不启动模型、不重发用户输入、不额外产生模型推理 token。Telegram 发起的输入不重复回显，已有回复路径保留。事件和定期核对共同工作，约 4 秒识别新对话，活动对话的记录核对约 15 秒一次；只发送完整回复。持久化消息键去重，断线可从最近 30 轮记录恢复；长时间离线超出这个窗口的内容不保证补齐。

仅同步用户可见的消息文字；图片输入显示附件占位，不自动读取上传本机文件。推理、工具执行记录及内部 agent 通信不转发。白名单撤销、关闭同步或话题失效会暂停；重新启用或重建话题时重新建立起点，旧队列保持旧话题，不改投其他位置。每个 Bot 仍只负责本机。

### 本机总览、Inbox 与派单

每个 Bot 只负责其所在机器的 Codex 会话。发送 `/tasks` 可分页查看本机已绑定会话、当前状态及最近回复；`/tasks all` 还会显示本机未绑定会话。未绑定会话需要先通过本 Bot 的 `/sessions` 接入，之后才能派单。查看总览只读取本机数据，不调用模型生成。`✅ 上轮完成` 表示最近一次执行结束，不代表整个项目已经完结。

`/inbox` 将本机原生等待输入／审批与最新一轮回复中明确提出的待确认问题分开标识。普通建议不自动视作阻塞；自然语言问题识别是保守规则，不能替代完整项目待办审查。业务问题可选择“回复此问题”，再回复 Bot 发出的指定消息；“已处理”和“稍后 1 小时”仅作用于本机。原生审批仍在原 Codex 客户端处理，稍后处理不会批准或解除原生等待。

在主对话或任意已授权的私聊话题发送 `@论文 检查最新批注`，或 `/to 论文 检查最新批注`。别名由桥接程序识别，不要求创建对应的 Telegram 用户。目标配置可增加 `"aliases": ["论文", "paper"]`；`/aliases` 只列出本机可用名称。别名重名时使用 `/to` 按钮选择具体会话。也可发送 `/to`，点击目标，再回复弹出的派单消息。回复只绑定该条指定消息，不会改变主对话原来的默认会话。

已绑定会话会立即生成名称别名，例如 `skyrim` 对应 `@skyrim`；新建的空会话无需先发送消息。索引同时保留配置中的别名和目标键，话题重建或解绑后以当前绑定为准。原生会话列表尚未包含该会话时仍可派单，总览显示“状态待同步”，直到取得实际状态；这些索引和菜单由桥接代码处理，不调用模型。

派单保存明确的本机原 thread ID 和话题 ID；恢复时不按别名重新选目标。目标绑定改变时会拒绝旧任务，不自动改投。回复保留在目标话题，并以正文汇总到本 Bot 的主对话；派单确认、按钮及回复提示也统一显示在主对话。派单目前支持文字，附件请直接发到对应话题。

本机队列自动运行，无需配置 SSH、汇总主机或 peers。外机别名、旧跨机按钮和直接注入的外机任务均会被拒绝；旧全局缓存不参与展示。升级时取消尚未投递的旧跨机任务；已经开始的原 Codex 任务继续由本机管理。历史记录保留，但不会继续跨机回传。旧的 `control_hub`、`control_hosts`、`control_peers` 配置不再启用任何跨机器能力，可删除。

## 附件与可靠性

Telegram 托管 Bot API 的附件下载上限为 20MB。图片作为 `localImage` 发送；其他文件下载到本机私有目录后提供文件元数据与本机路径。相册聚合后作为一次输入。

语音和视频目前按文件接收，没有自动转写或抽帧。生成文件可通过公开回复中的明确本机下载链接回传，规则见“图片与文件回传”。转接层不自动执行或解压附件，也不向模型暴露带 Token 的下载链接。

消息接收与 offset 原子提交。每条输入和回复保留自己的会话与话题，切换和重建入口不会把旧任务结果转发到另一个会话。Telegram 发信没有幂等键，因此发信成功但本地尚未提交时崩溃，仍可能重复投递一次回复。

删除话题后可使用 `/sessions` → 选择原会话 → **重新创建话题** → 确认，保留原 Codex 历史。旧话题的未送达回复会保留，不自动重发或重复执行任务。

## 版本维护

两台机器使用同一个源码仓库，各自保留 Bot Token、白名单和运行数据库。修改通过测试后提交，再发布版本 tag，并分别更新机器；更新与回退流程见 [DEPLOYMENT.md](DEPLOYMENT.md)，功能记录见 [CHANGELOG.md](CHANGELOG.md)。

`.github/workflows/tests.yml` 为推送和 Pull Request 配置 Python 3.10 / 3.12 自动测试。GitHub 仓库建立并推送后才会实际运行该工作流。

## Codex 选项按钮

话题模式中，发送 `/model`、`/effort` 或 `/format` 可打开设置按钮菜单，三类菜单之间也可直接切换。当前选中项带勾，模型列表支持分页，推理强度只列出当前模型支持的级别；点击选项直接保存并回读确认。模型及强度取自当前机器的实时 Codex 目录，修改用于后续轮次，不启动或中断当前任务；回复格式切换当前会话的 Rich Markdown 或纯文本偏好。仍可直接发送 `/model 模型ID`、`/effort 级别` 和 `/format rich` 等文字命令。

菜单及操作结果留在输入所在话题，绑定原 Codex 会话；在 All 打开时明确显示并操作原 Manager 根会话。菜单过期、原绑定变化或当前模型已变更时会提示刷新，不把旧强度选择应用到另一个模型。重复按钮、重启及未知修改结果不会自动重复覆盖设置，设置菜单本身不调用模型。

当前页面对应的“模型”“强度”或“格式”导航标签显示为禁用按钮，不生成回调；切换到其他页面后会重新启用。旧菜单发送的当前页回调也不会重新查询或重置页码，刷新及跨页导航保留原行为。

话题模式自动把 Codex 的原生结构化选择题显示为对应话题中的独立按钮消息，无需新建或重新绑定会话。单题点选后提交，多题逐题选择并在最后一题提交；“自行输入”会发出文字回答提示，回复该提示即可作答，回复 `/cancel` 只取消此次文字输入。普通聊天与系统指令继续按原有流程处理。

多题问题中，回复文字提示完成一道题后，桥接会为下一题另发包含题号与选项的回复提示。已填答案保留，最后一题完成后才一起提交；再次回复上一题的旧提示会说明当前进度，并引导使用新的入口，不会把文字误记为下一题答案。下一题提示的发送进度持久保存，发送结果未知时不重复创建，也不自动补发旧答案。

问题会立即发送，不等待当前任务完成或合并正文；点击后答案回到原 Codex 会话，同步问题使用原请求响应，异步问题使用原生关联答案格式。问题查询和按钮界面由代码处理，提交后 Codex 按原会话的模型及参数继续工作。已回答、已过期或绑定变化的按钮会失效；也可以在 Codex 客户端回答，桥接会随后关闭对应按钮。首次启用不补发旧问题，普通正文中的 A/B/C 列表不会自动变成选择题。

本功能不代替执行审批、权限授权或机密输入。原生接口暂不能核验的问题仍需在 Codex 客户端处理；连接或发送结果未知时不会自动重复提交。问题默认有效期 24 小时，同步问题还受原生请求生命周期限制。

异步答案提交前只核验原问题所在轮次及其后的记录，避免长会话的旧历史耗尽等待时间。若等待提交锁或核验时超时，且尚未进入发送阶段，会明确提示“答案尚未提交”，保留有效问题供你手动重试；已进入发送阶段但结果未知时仍提示待核对，不自动重发。升级不会补发之前失败或未确认的答案。

旧会话接口若只返回临时问题编号，桥接会读取原会话的本机记录，精确核对会话、轮次及原始问题 ID；无法核对时不提交答案，也不按问题文字猜测目标。

若在 Codex 客户端先回答了多道题中的一部分，Telegram 会关闭该组按钮以避免重复提交，其余问题请继续在 Codex 中回答。

All 派单和 Codex 客户端用户输入回显中，桥接生成的“你在 All 说”“你在 Codex 客户端说”标题保持普通文字，仅用户消息正文使用引用格式。纯文本降级仍保留原文，附件与模型输入保持原流程。

使用 `status-bar` 或 `status-draft` 累计预览时，任务运行中接受新的普通输入或每道选项回答后，后续预览会静音重建到最新位置，显示在新回复之后，保留累计内容并继续编辑新消息；All 派单和本机客户端用户回显成功发送后也会更新位置。系统查询、取消和重复点击不触发移动。新预览确认成功后才清理旧预览，重启保留位置水位；创建结果未知时不会盲目重发。静音使用 Telegram 的 `disable_notification`，不保证客户端完全不出现通知横幅。

## 独立故障提示

可选的 `recovery_service.py` 使用独立用户服务监控消息接收器，不接收 Telegram 更新、不调用模型、不改写输入队列，也不自动重启接收器。遇到 `getUpdates` 轮询冲突等退出时，原程序先保存故障原因和受影响话题；独立服务在这些原话题发送故障提示及待处理消息、附件数量。接收恢复后更新同一条提示。没有可定位的工作话题时才回到原 Manager 根话题。

在本机原有状态目录下另建 `recovery/config.json`，不要替换主 `config.json`：

```json
{
  "enabled": true,
  "mode": "alerts-only",
  "interval_seconds": 5
}
```

前台运行 `python3 recovery_service.py run --state-dir ~/.local/state/codex-telegram`；长期运行可将 [独立用户服务示例](contrib/codex-telegram-recovery.service) 安装为 `~/.config/systemd/user/codex-telegram-recovery.service`，按实际克隆目录修改路径，再执行 `systemctl --user daemon-reload` 和 `systemctl --user enable --now codex-telegram-recovery.service`。服务及其配置目录应仅对本机用户可读，使用主桥接已有 Bot 身份与白名单，不复制凭据。

可用 `python3 recovery_service.py status` 查看独立健康状态，`journalctl --user -u codex-telegram-recovery.service` 查看日志。`python3 recovery_service.py probe --target 会话key` 会向当前绑定话题发送明确标记的测试提示并原地更新，不中断任务；测试不是实际故障。`manage.py` 另支持显式 `--state-dir` 和 `--session-name`，手动停止时写入短期维护标记，避免部署期间误报。

仅告警模式不监听 HTTP 端口，不提供网页恢复按钮，也不启用 Funnel。轮询冲突持续时保持停止，由维护者查明重复接收器后恢复；不能用无限重启争抢同一个 Bot。机器停机、网络不可用或 Bot 凭据失效时，Telegram 提示可能无法送达，应同时检查本机独立服务健康状态。发送结果未知时保留记录、不盲目重复发送。

## 可选提醒示例

`bus_reminder.py` 和 `manage_bus_reminder.py` 是独立的九巴末班车提醒示例。配置与状态默认位于 `~/.local/state/kmb72-reminder/`，需要另行配置；启动聊天桥接不会自动启用提醒。它们不接收 Telegram 更新。

如需在电脑扬声器播放语音，在现有 `config.json` 中明确设置以下字段，保留原有线路与站点配置：

```json
{
  "delivery_mode": "local_audio",
  "audio_device": "default:CARD=Generic",
  "start_minute": 20,
  "end_minute": 60,
  "interval_seconds": 60,
  "lead_minutes": 12
}
```

此示例每天香港时间 00:20–01:00 检查末班车到站时间，预计到赤泥坪前 12 分钟内播放一次。`audio_device` 必须按本机声卡选择，可用 `aplay -L` 查看；`Generic` 只是设备示例。播放依赖 Linux ALSA 的 `/usr/bin/aplay`（`alsa-utils`）和支持 MP3 解码的 `libsndfile`，运行账号须有声卡访问权限。电脑需保持开机、扬声器取消静音并设置合适音量，提醒程序本身不修改音量。

本机正式提醒使用独立缓存 `alert-local.mp3`，首次预制语音需要联网，内容不包含 Telegram 的文字查看指引；旧 Telegram 缓存 `alert.mp3` 保留。`local_audio.py` 将语音转换成经过校验的同名 PCM WAV 缓存，再等待本机播放完成，播放阶段不访问网络；实时到站查询仍需要联网。可先运行 `python3 bus_reminder.py prepare` 预制正式语音，再运行 `python3 manage_bus_reminder.py test-voice` 测试本机扬声器。测试使用 `test.mp3`，不会发送 Telegram 消息，也不会占用当晚的真实提醒；`check` 仅查询到站数据，不播放提醒。

`local_audio` 模式不读取 Bot Token、桥接配置或白名单，也不向 Telegram 发送语音、文字或故障通知。播放失败会记入日志和健康状态，保留后续检查的重试机会，不降级为 Telegram 提醒；只有成功播完才保存当晚已提醒记录，正常重启后继续去重。若需要原有 Telegram 投递方式，明确设置 `"delivery_mode": "telegram"`；省略该字段也保留原来的 Telegram 行为。
