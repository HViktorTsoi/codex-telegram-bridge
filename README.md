# Telegram ↔ Codex bridge

用一个 Telegram Bot 控制本机 Codex 会话，支持绑定已有会话或新建会话。绑定已有会话时保留原历史、模型和权限设置。这是通过 Codex app-server 工作的 Python 桥接程序。

## 让其他 agent 配置

可以把仓库地址和下列文字发给目标机器上的 agent。私有仓库需要先为该机器或 agent 使用的 GitHub 账号配置读取权限；Bot Token、Telegram 用户 ID 和实际会话绑定不在仓库里，需要在目标机器上配置。环境要求见下方“环境”一节。

```text
请部署 https://github.com/HViktorTsoi/codex-telegram-bridge，使用 v0.11.9 或更新的稳定版本。

先阅读 README.md、DEPLOYMENT.md 和 TOPICS.md，检查目标机器的 Python、tmux 和 Codex 服务。
复用本机已有 Codex app-server，列出并核对我要绑定的原 session；绑定时保持原 thread ID，不新建或 fork。
只有我明确选择 /sessions 的“新建会话”并确认时，才调用 thread/start；新会话使用本机默认模型和权限，创建本身不调用模型生成。
总览、Inbox 和派单只管理本机会话，不配置任何跨机器同步或路由。
All 中的普通消息默认必须选择接收会话并确认后才投递；不要恢复为自动转给默认或最近会话。明确 @别名、/to 和系统指令沿用原流程。
使用独立 Bot 和私有配置目录，避免与已有实例争用同一个 Token；将访问策略设为仅允许本人 Telegram 用户 ID。
按需引导我开启 BotFather Threaded Mode；多会话模式应创建真实 Telegram 话题并保存返回的 topic ID，替换示例里的占位值。
在 BotFather 开启 Disallow users to create new threads，保留 Threaded Mode，让管理命令能留在主对话而不会被客户端自动建话题。
安装依赖并运行测试，再启动对应实例；manage.py 只管理默认实例，独立状态目录需使用 bridge.py 或 topics_bridge.py 的 run --state-dir 入口，不要误操作已有实例。
验证 /status 中的原 thread ID、Markdown 和图片输入；多会话模式还需验证 /sessions 和各话题的消息归属。
按需启用 native_mirror，将本机 Codex 客户端新消息和回复同步到对应话题，不补发启用前的历史。
如需将正文通知集中在任务结束时，在话题模式配置中设置 notification_mode: completion；中间正文使用累计草稿预览，完成后合并为一条或少量几条，最后一条正文带完成提醒，图片单独发送。
如需整块进度预览，可设置 preview_style: block；当前 iPad 已实测整段显示，其他客户端先验证，兼容性需要时使用 plain。
如需状态栏与正文分成两个聊天气泡，可设置 preview_style: status-card；状态消息首次静音创建，之后复用原消息编辑，正文单独使用累计草稿。首次创建仍可能显示静音横幅，固定状态消息不会一直位于聊天最底部。
缺少必要配置时再向我索取；Bot Token 只保存在目标机器私有凭据文件中，不提交到 GitHub。
```

目前支持的能力见下方“功能”。本机图片支持自动回传；其他文件自动回传尚未实现。

## 功能

- 文字、图片、文件、相册、位置、联系人和投票输入。
- Telegram 引用回复附带易读的原消息正文和选中片段，帮助 Codex 理解“改这里”等指代。
- Codex 回复中的明确本机图片链接会上传为真实 Telegram 图片，支持 PNG、JPEG、WebP、GIF，适用于二维码、截图和图表；不依赖 `/format rich`。
- 一个私聊内用不同话题连接不同 Codex 会话。
- All 防误发：普通文字、图片、文件及相册先暂存，选择本机会话、核对并确认后才发送；未确认时不调用模型。
- `/sessions` 按钮流程：按名称和工作目录查看本机会话 → 选择 → 核对完整 ID → 确认绑定到新话题。
- 会话选择按最近实际使用排序；已绑定会话可用“修改名称”或 `/rename` 同步修改 Codex 会话名和 Telegram 话题名。
- `/sessions` →“新建会话”：按钮浏览本机文件夹、输入路径或新建文件夹，填写名称并确认后创建空 Codex 会话并连接新话题。
- 已绑定会话可通过按钮重新创建话题，恢复删除后的入口。
- 可选话题内工作状态消息：两行显示用时、待处理、完成、停止和断连状态，跟随新回复和图片到对话底部，覆盖从电脑端发起的任务。
- 可选仅完成时通知：中间回复与两行状态合并为每 15 秒更新的累计草稿，整轮结束后合并发送完整正文，最后一条带完成提醒，图片单独发送。
- 可选本机客户端消息同步：复制客户端的新输入和 Codex 回复到绑定话题，避免重复回显 Telegram 消息。
- `/tasks` 本机会话进度、`/inbox` 待处理事项、`@别名` 和 `/to` 本机派单。
- 话题模式的全局菜单和派单汇总显示在主对话，会话参数、停止等指令的回复发回输入所在对话。
- Codex 回复默认使用 Telegram Rich Markdown 排版，支持标题、表格、代码块和公式；可按会话切换纯文本。
- `/model`、`/effort` 查询和修改对应会话的参数；`/status` 核对绑定；`/stop` 停止对应会话的任务。
- 持久化收发队列、重复更新去重、按原目标恢复任务，未确认的输入不盲目重复执行。

每个 Bot 只接受配置的白名单用户的私聊。同一个 Token 只能运行一个更新接收器。

## 环境

- Linux、Python 3.10 或更新版本、tmux。
- 可访问的 Codex app-server Unix socket，且该服务能读取目标已有会话。
- Telegram Bot Token、本人 Telegram 用户 ID。

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m unittest discover -v
```

自动测试使用模拟 Telegram 和本机临时 socket，不需要真实 Token 或 Codex 登录。

## 配置

代码和每台机器的配置分开保存：

| 内容 | 默认位置 |
|---|---|
| 桥接配置、SQLite、日志、健康状态 | `~/.local/state/codex-telegram/` |
| Bot 凭据、访问白名单 | `~/.claude/channels/telegram/` |
| Codex socket 示例 | `~/.codex/app-server-control/app-server-control.sock` |

socket 路径应指向实际使用的已有服务；使用另一个新服务不等于接入桌面上正在使用的会话。配置中的路径需要填写为本机绝对路径。

参考 [config.single.example.json](config.single.example.json)、[.env.example](.env.example) 和 [access.example.json](access.example.json)，在上述私有目录中创建实际配置。Token、owner ID、socket 路径和已有会话 ID 都需要替换；核对完成后将 `setup_required` 改为 `false`。目录权限使用 `700`，凭据和状态文件使用 `600`。

绑定已有会话时应先用 `thread/read` 核对标题、ID 和历史，再用 `thread/resume` 恢复同一个 ID。程序不以 `thread/start` 或 `thread/fork` 作为绑定失败后的替代方案。

### 多会话话题模式

1. 在 BotFather 为该 Bot 开启 Threaded Mode / Topics，并开启 **Disallow users to create new threads**。
2. 将原会话绑定到一个 Telegram 私聊话题，参考 [config.topics.example.json](config.topics.example.json)。
3. 启动后发送 `/sessions`，点击“添加会话”绑定已有会话，或点击“新建会话”创建全新会话；无需重启。
4. 已有会话若尚未出现在列表中，点击“重新加载”；尚未持久化的电脑端草稿可能需要先发送首条消息。

`/sessions` 首页逐项显示已绑定会话的名称和工作目录。“添加会话”首先列出本机现有会话涉及的所有工作目录，每个目录按钮显示路径和会话数量；选中目录后，才展示其中的 sessions。目录列表超过 12 项时可翻页，使用“返回目录列表”可重新选择。会话页面顶部只显示一次路径，下方只列出该目录的会话名称按钮；也可用“上个目录／下个目录”快速切换。目录未提供时单独归组，较长路径保留首尾。此操作只读取本机会话元数据，不调用模型生成。

`/sessions` 首页、All 的接收会话选择、`/to` 和 `/rename` 的选择列表按最近使用在前排序。“添加会话”中的目录按其中最近使用的会话排序，同目录内也按最近使用排序；没有使用记录时保留原生列表的最近更新顺序。使用记录按原 Codex 会话 ID 持久保存，包括已接收的话题消息及会话指令、确认发送的 All 消息、已投递的派单和完成的改名。单纯点开话题的浏览时间无法从 Bot API 获取；仅查看菜单、取消选择、机器人回复及状态刷新不会更新顺序，也不将电脑端单独使用时间当作 Telegram 访问记录。

同一目录超过 12 个会话时在该目录内分页；选择会话后返回列表会保留当前目录和页码。打开列表时读取完整的原生分页结果再分组；目录快照持久化，切换目录和翻页使用同一份快照，避免其他会话更新导致列表跳动。点击“重新加载”更新数据并保留当前目录；长时间未操作导致列表过期时可重新加载。

“新建会话”流程从本机用户主目录开始，点击文件夹进入、点击“上级目录”返回，也可显示点号目录。子目录每页 10 项。“输入路径”支持绝对路径、`~/` 和相对于当前目录的路径；“新建文件夹”只创建当前目录下的一层，支持中文和空格，不覆盖同名文件或文件夹。新建后进入该文件夹，仍需点击“使用当前目录”确认工作目录。

路径、文件夹名和会话名称通过 Telegram **回复输入提示**填写，手机通常会自动进入回复状态；若没有，请长按提示选择“回复”。只有回复指定提示的文字才进入该流程，普通消息继续正常聊天。回复提示 `/cancel` 或点击“取消”可取消；已经新建的文件夹会保留。普通选择和输入提示有效期为 15 分钟。

填写名称后展示主机、目录和名称，点击“确认新建并连接”才调用 `thread/start`，再用 `thread/name/set` 命名并绑定返回的同一个 ID。新会话继承本机 Codex 默认模型和权限，不复制原会话的历史；直到你在新话题发送消息才调用模型生成。接口依据 [Codex 官方 app-server 文档](https://learn.chatgpt.com/docs/app-server)，本机 app-server 需支持这两个方法。已有会话的绑定和修复仍不会调用 `thread/start` 或 `thread/fork`。

创建记录持久化到私有 SQLite：重复点击不会重复创建；创建成功后命名或绑定失败，可在 `/sessions` 首页点击“继续处理”沿用已记录的新会话 ID。若 `thread/start` 或 `createForumTopic` 的返回结果丢失，会提示先核对已有会话或话题，不自动重建。

### 修改会话名称

发送 `/sessions` → 选择已绑定会话 →“修改名称”，回复名称输入提示，再点击“确认改名”。也可在对应话题输入 `/rename`，或 `/rename 新名称`；在 All 输入该命令会先选择目标，不默认使用最近会话。名称输入、核对和结果面板统一显示在 All；只有回复指定名称提示的文字进入改名流程，回复 `/cancel` 或点击“取消”可退出。

确认后依次更新原 Codex 会话名、同一个 Telegram 话题名和本机绑定记录。会话 ID、话题 ID、历史、正在执行的任务、模型和权限保持原值；既有显式别名和 target key 继续可用。改名只使用元数据接口，不调用模型生成。名称须为非空单行，最多 90 个 UTF-16 单元（部分表情占两个），不能与本机其他已绑定会话重名。

改名进度持久保存；Codex 已改名而 Telegram 暂时同步失败时，可在 `/sessions` 首页或该会话的“修改名称”入口点击“继续同步名称”，沿用原会话与话题继续处理。绑定或名称在同步中被其他操作修改时会停止并提示核对，不改投其他会话；话题已失效时先修复绑定。

`root_target` 继续提供原会话及主对话系统指令的上下文；All 普通内容默认先选择并确认目标，再投递到所选话题。话题模式、恢复策略和完整配置说明见 [TOPICS.md](TOPICS.md)。

上述 BotFather 开关阻止 Telegram 客户端在主窗口发送 `/tasks`、`/sessions` 等消息时先自动创建话题。可用 `getMe` 验证 `has_topics_enabled=true`、`allows_users_to_create_topics=false`；此开关需要 Bot 所有者在 BotFather 设置，Bot Token 无法修改。它同时禁止用户手动新建、编辑和删除话题，桥接仍可通过 `/sessions` 创建和重建绑定话题。参见 [Telegram 官方说明](https://core.telegram.org/api/forum#bot-forums)。

话题模式中，`/sessions`、`/tasks`、`/inbox`、`/to`、`/aliases`、`/help`、`/start` 等全局菜单及派单汇总发送到主对话；旧话题里的管理菜单按钮会在下一次操作时转到主对话。`/status`、`/model`、`/effort`、`/format`、`/stop` 作用于输入所在话题对应的原 Codex 会话，查询结果、确认和错误提示均发回输入所在对话；在主对话输入则回复主对话。未知命令及未绑定话题中的会话指令错误也回复原处，未绑定会话不会改投默认目标。发送层只显示正文，不自动添加 `〔会话标题〕` 前缀。普通对话、图片和状态提示继续使用原话题；已有发信队列保留原来保存的位置。

直接输入 `/sessions` 使用独立的菜单处理通道，首页读取本机已保存的目录信息，无需等待正在执行的任务或较早的目录查询、绑定、改名操作。尚无缓存的目录会显示待同步，后续原生元数据读取会补充；缓存只用于显示，实际绑定与重建仍重新核对原生会话身份。

### All 防误发

在 All 输入普通文字或发送附件后，桥接会先展示本机已绑定会话的选择按钮；点击一个会话后，再核对会话名称和消息内容，点击“确认发送”才进入该会话的输入队列。点击“取消”不发送。每条普通消息分别确认，不会记住上次选择，也不会自动投给 Manager 或最近活跃会话。后续回复直接在所选话题显示。

确认后，原始文本或附件说明文字也会以“📩 你在 All 说：”同步到所选 Telegram 话题，连同原先保存的易读引用上下文，方便在该话题连续阅读。文字显示使用持久化发送队列，重复确认及重启恢复不会重复入队，也不会额外调用模型。启用仅完成时通知后，这份原文也在完成时静音发送。此处只复制文字，不复制图片或文件本体到 Telegram 话题；附件仍按原流程交给 Codex。取消或未确认时不显示，不补发之前已完成的历史记录。

相册会先收齐同组附件再展示一个入口；确认前新到的附件会使旧确认失效，需要重新核对。确认后才到达的后续附件另外暂存，不会自动沿用先前目标。原文字、附件及引用上下文随消息保留；确认前不下载附件、不调用 Codex 模型。

暂存和确认记录持久化，重启后仍可处理；通过 `/sessions` →“待发送”找回未发内容。目标绑定在选择、确认和实际调用模型前都会核对，绑定变化时不自动改投。已有话题内的普通聊天直接进入原会话；斜杠系统指令、明确的文字 `@别名`、`/to` 和既有指定输入提示回复沿用原流程。附件 caption 中的 `/stop`、`@别名` 等只作为附件文字，不执行指令。

`All` 的位置由 Telegram 客户端控制，插件不能在它左侧插入空白标签；防误发流程使用 All 内的普通按钮，不新建空白话题。

### 图片回传

让 Codex 在回复中使用 `![说明](/本机绝对路径/图片.png)`，带空格的路径可写成 `![说明](</本机路径/图片.png>)`。指向受支持图片的普通本地文件链接也会上传。仅处理公开回复中的明确链接；代码示例、用户输入、远端 URL、相对路径和其他文件不会触发本机上传。单图上限 20 MB；超过 Telegram 照片限制的图片、GIF 或被明确拒绝为照片的图片会按原文件发送。

如果最终回复明确表示“已附上图片”等，却没有图片链接，桥接会补上该轮最后一张 `imageView` 图片；不会因为 Codex 内部查看截图就直接发送，也不会从其他轮次取图。多图请逐一使用明确图片链接。桌面端回复同步沿用相同规则；用户在桌面输入的图片仍只显示附件提示。

图片先保存到对应会话私有目录的 `outgoing-images/`，再进入持久化发送队列，避免二维码刷新后把旧消息替换成新文件。照片上传使用 `sendPhoto`，文件发送使用 `sendDocument`，都保留原话题；`/format plain` 也能收图。结果不明或上传过程中重启时，图片标记为待核对并停止自动重发，防止重复图片；429 限流按原快照延迟重试。格式化失败不会触发另一份图片上传。启用后不补发历史回复。

## 运行与命令

在代码目录中运行：

```sh
.venv/bin/python manage.py start
.venv/bin/python manage.py status
.venv/bin/python manage.py logs
.venv/bin/python manage.py stop
```

`manage.py` 根据 `config.json` 的 `mode` 选择单会话或话题模式。单会话首次启动可使用 `start --notify`；话题模式使用 `/sessions`。电脑、网络和 Codex 服务需要保持运行；当前没有配置开机自启。

| Telegram 命令 | 操作 |
|---|---|
| `/sessions` | 话题模式下打开会话列表、添加和重建入口 |
| `/rename`、`/rename <新名称>` | 话题模式下确认修改原 Codex 会话名，并同步 Telegram 话题名；All 中先选择目标 |
| `/tasks`、`/tasks all` | 查看本机已绑定会话，或包括未绑定会话的本机完整目录 |
| `/inbox` | 查看原生等待和最新回复中的待确认问题，回复、稍后处理或标记已处理 |
| `/to`、`/to <别名> <任务>` | 按钮选择目标派单，或直接指定原会话 |
| `/aliases` | 查看可用的本机 `@别名` 派单名称 |
| `/model`、`/model <ID>` | 查询或切换当前目标会话的模型 |
| `/effort`、`/effort <级别>` | 查询或修改当前目标会话的推理强度 |
| `/format`、`/format rich`、`/format plain` | 查询回复格式，或切换排版与纯文本 |
| `/status` | 显示主机、会话名称、完整 ID 和参数 |
| `/stop` | 停止当前目标会话的任务 |
| `/help` | 查看说明 |

参数命令调用 `thread/settings/update` 并回读确认，不启动模型生成。普通消息沿用原会话设置。原 Codex 客户端继续处理审批和其他交互请求。

### 引用上下文

在 Telegram 长按某条消息并选择“回复”，随后发送新要求。桥接会在本次输入后空行分段，以易读正文附加引用内容，明确区分新要求与被回复的材料。手动选中的片段优先显示，原消息正文随后供参考；两者相同时不重复。消息 ID、话题 ID 等元数据保留在内部记录中，不发送给模型。普通文字、富文本中的标题、表格和代码都可提取；相册重复的同一引用只附加一次。例如：

```text
把这句话翻译成英文

［引用内容］

> 需要翻译的原文。
```

没有引用时，原消息和输入结构保持原样；命令仍按原规则处理，不因引用额外启动模型。新消息里的图片、文件和相册继续使用现有附件流程。引用原文最多保留 12,000 字符，选中片段最多 4,000 字符，超长时标记截断；原文未随 Telegram 更新提供时明确标记不可用，不猜测或抓取历史。

被引用的附件只提供类型、文件名及说明，不自动重新下载；需要模型看原图或原文件时，请重新附上。引用只帮助理解内容，不改变当前话题对应的 Codex 会话；`@别名` 和 `/to <别名> <任务>` 仍以明确目标派单，同时保留引用。`/to` 按钮和 Inbox 的指定回复继续使用原绑定流程。

### 回复排版

默认将新的 Codex 正式回复通过 `sendRichMessage` 发送，使用 Telegram 的 Rich Markdown。菜单和其他控制回复使用普通文字；普通状态卡使用 Rich HTML 加粗，累计草稿可选纯文本或整块进度预览。客户端需要支持 Telegram Rich Messages。

在对应会话发送 `/format rich` 开启排版，`/format plain` 改为纯文本，`/format` 查看当前选择。选择按目标会话持久化，对之后生成的回复生效，不更改模型参数。

长回复按段发送；代码围栏会在分段处补齐，原始文字另行保留。服务端明确拒绝格式或不支持富文本接口时，发送同一段原文。话题不存在、权限、限流和送达结果不明的网络错误不会被当作格式错误降级。逐条发送模式保留旧队列的内容和分段；仅完成时通知模式会合并尚未发送的正文，已经开始发送的分段保持固定。更新不会将已经投递的历史重新发送。

回复中的本机 Markdown 文件、图片链接会显示为名称和路径，避免 Telegram 尝试读取本机路径而使整条回复退回纯文本。本机图片会明确标注“尚未上传”；公网链接和代码示例保留原样。这一步不读取或上传文件。

### 仅任务结束时通知

在话题模式的 `config.json` 顶层设置 `"notification_mode": "completion"`，重启对应实例后启用；也可在单个 `targets` 项上设置，该目标的配置优先。省略配置或使用 `"notification_mode": "all"` 保留逐条发送的原有行为。此选项不改变单会话模式。

普通任务消息写入本机接收队列后，独立预览流程会立即尝试显示“已收到，正在准备”，无需等待附件处理、Codex 启动请求返回、首条回复或历史读取。连接未就绪时显示等待连接，投递结果尚不明确时显示正在核对；实际可见时间仍取决于 Telegram 和网络。此流程覆盖话题内消息、确认后的 All 消息及已投递的派单；系统指令、空消息、无权限输入和未确认的 All 消息不触发。向正在执行的任务补充消息时保留已有累计正文，取得真实任务 ID 后继续使用同一预览。

任务执行期间，中间正文使用临时草稿预览，每约 15 秒用累计内容更新。预览保留截至当前的文本；超过 3800 个 UTF-16 单元时，明确标注只显示最近部分，完整文本和图片仍保存在持久化队列中。草稿暂时失败或不受支持时，正文继续暂存到任务结束，不改发普通进度消息。草稿本身是临时显示，停止刷新约 30 秒后会消失，参见 [Telegram 草稿接口](https://core.telegram.org/bots/api#sendmessagedraft)。

设置 `"preview_style": "status-card"` 可将状态栏与正文放在两个独立的聊天气泡中：两行状态使用普通消息，每个原生会话、接收账号与话题的固定绑定首次静音创建一次，之后每约 15 秒编辑同一个消息 ID，并在后续任务中继续复用；累计正文单独使用整块草稿，沿用同一轮固定的草稿标识。尚无正文时只显示状态消息，最终正文获得发送确认后再更新状态为完成、失败或停止。状态消息位置固定，不会自动移到聊天最底部；首次创建可能产生一次静音横幅，后续更新只编辑原消息。参见 [Telegram 消息编辑接口](https://core.telegram.org/bots/api#editmessagetext) 和 [静音发送参数](https://core.telegram.org/bots/api#sendmessage)。

可选设置 `"status_card_pin": true` 会尝试把该绑定自己的状态消息静音加入聊天的置顶列表；默认关闭，支持顶层及单个目标配置。置顶操作不更换状态消息、不清除其他置顶，正常刷新和后续任务继续编辑同一个消息；置顶请求失败不影响正文草稿，发送结果未知时不会自动重复置顶。Bot API 没有控制置顶栏显示在 All 或话题顶部的参数，接口返回成功也不代表已确认客户端的展示位置。已有 iPad 使用反馈显示置顶只出现在 All 顶部，因此不能将该选项视为每个话题内固定状态栏的方案。参见 [Telegram 置顶接口](https://core.telegram.org/bots/api#pinchatmessage)。

设置 `"preview_style": "block"` 保留同一条草稿内部的两个区块：上方两行状态，下方累计正文，客户端仍将它们显示在同一个消息气泡中。尚无正文时只显示状态区块。`status-card` 与 `block` 的正文都使用 thinking 区块，此前 iPad 实测确认该区块文字整段出现；具体布局仍取决于客户端。设置位置支持配置顶层或单个目标，目标配置优先。省略该项或使用 `"plain"` 保留状态与正文合并的纯文本草稿，逐字动画由客户端控制。草稿依赖客户端支持，旧客户端可能不显示，可切回 `plain`。轮换标识不能可靠关闭动画，部分客户端反而会重新动画全文，参见 [Telegram 流式预览说明](https://core.telegram.org/api/bots/ai)。

只有原生任务明确进入 `completed`、`failed` 或 `interrupted`，且完整历史已读取成功，才释放这一轮的正式过程、结果和图片。暂存正文按原顺序合并，每条原始子消息之间使用空行与 `────────────` 分隔线；同一条消息因长度产生的内部切片直接拼接，保留原文。通常发为一条，长文按每条最多 3800 个 UTF-16 单元拆分，代码围栏在分段处补齐，完整内容保留。图片单独静音发送，完成、失败或停止提示合入最后一条正文；只有最后一条文字使用正常通知，前面的文字分段静音发送，不再额外发送一条完成提醒。`final_answer` 中间项、等待你输入／审批、断连或未知状态都不会被误认作整轮完成。电脑端镜像任务沿用相同规则，不补发旧的已完成历史通知；`/sessions`、`/model` 等主动系统操作仍可正常回复，不会被暂存的任务内容堵住。

完成记录与通知意图持久保存；重启及重复事件不重复生成完成提醒，发送结果不明时不自动重发该提醒。此功能只管理显示和发送时机，不额外调用模型，也不改变会话 ID、历史、任务或参数。正常提醒仍受手机的 Telegram 静音和勿扰设置影响。Telegram 的“静音发送”只保证无声音，不能保证所有系统都不显示横幅。`plain` 和 `block` 在任务进行时只发送草稿；`status-card` 另有一次独立状态消息的静音创建，随后复用编辑。具体手机草稿效果仍需实测。[通知参数说明](https://core.telegram.org/bots/api#sendmessage)

### 话题内工作状态

以下普通状态卡行为适用于 `notification_mode: "all"`；`completion` 模式按上文 `preview_style` 显示草稿或复用独立状态消息。

话题模式可在 `config.json` 的单个 `targets` 项中设置 `"activity_indicator": true`，重启对应实例后启用。也可在配置顶层开启，单个目标的设置优先；默认关闭，便于先在一个话题试用。

每次观察到对应原 Codex 会话正在执行任务时，在绑定话题发送一条静音状态消息，随后每约 15 秒更新用时。默认 `activity_position: "bottom"`：有新回复、图片或普通用户消息时，确认新状态卡已在下方发送成功后删除旧卡；没有新内容时只编辑当前卡，不会每 15 秒新增消息。等待输入／审批、完成、失败、停止和连接中断会触发状态变化。电脑端发起的任务同样可见；状态只通过原会话的元数据和任务记录读取，不发起模型生成。

状态跟随最新内容，通常在下一次可更新时移到底部，最多约 15 秒；它是普通聊天消息，不固定悬浮在屏幕边缘。完成提示也会跟随该轮最后送达的回复或图片，其他任务的新消息不会让旧完成提示重新出现，启用时不补发历史状态。可在全局或单个 target 设置 `activity_position: "inline"`，恢复原地更新。

状态提示使用两行紧凑布局，话题标题负责显示会话名。第一行在状态两侧添加 `━━━━` 分隔线，第二行显示用时和更新时间；等待处理时会在第二行提示前往 Codex。例如：

```text
━━━━ ⏳ 正在工作 ━━━━
2分18秒 · 更新 22:05:30
```

状态消息包含最后更新时间；中间回复不会被当作任务完成。重启后复用已保存的消息 ID，完成后的旧任务不补发状态。删除或重建话题后，不会把旧状态消息改投到其他话题。该功能是周期采样，短于采样间隔的任务可能没有工作中提示；启动时已完成的任务不会创建新状态消息。发信结果不明时不盲目重发，避免重复；网络恢复后有已知消息 ID 的状态可继续更新。

第一行使用加粗正文配色，配合彩色状态图标保持醒目和可读性。保留两行布局，单纯样式升级仍原地编辑；明确的格式拒绝会降级为纯文本。底部换卡的意图与旧卡清理持久化，旧卡只在新卡发送确认后删除；发信结果不明时不重复换卡，已知限流延迟重试，删除重试不会再次创建新卡。

### Codex 客户端消息同步

话题模式可在配置顶层设置 `"native_mirror": true`，或在单个目标上启用／关闭，单个目标优先。默认关闭。开启后首次观察会话时建立同步起点，不补发当时已有的消息；以后在 Codex 客户端发出的新输入与公开的 Codex 中间回复、最终回复会复制到对应 Telegram 话题。用户输入标注“你在 Codex 客户端说”，由 Bot 代发；普通会话操作继续使用同一个原 thread ID。

同步只读取本机原会话记录，不启动模型、不重发用户输入、不额外产生模型推理 token。Telegram 发起的输入不重复回显，已有回复路径保留。事件和定期核对共同工作，约 4 秒识别新对话，活动对话的记录核对约 15 秒一次；只发送完整回复。持久化消息键去重，断线可从最近 30 轮记录恢复；长时间离线超出这个窗口的内容不保证补齐。

仅同步用户可见的消息文字；图片输入显示附件占位，不自动读取上传本机文件。推理、工具执行记录及内部 agent 通信不转发。白名单撤销、关闭同步或话题失效会暂停；重新启用或重建话题时重新建立起点，旧队列保持旧话题，不改投其他位置。每个 Bot 仍只负责本机。

### 本机总览、Inbox 与派单

每个 Bot 只负责其所在机器的 Codex 会话。发送 `/tasks` 可分页查看本机已绑定会话、当前状态及最近回复；`/tasks all` 还会显示本机未绑定会话。未绑定会话需要先通过本 Bot 的 `/sessions` 接入，之后才能派单。查看总览只读取本机数据，不调用模型生成。`✅ 上轮完成` 表示最近一次执行结束，不代表整个项目已经完结。

`/inbox` 将本机原生等待输入／审批与最新一轮回复中明确提出的待确认问题分开标识。普通建议不自动视作阻塞；自然语言问题识别是保守规则，不能替代完整项目待办审查。业务问题可选择“回复此问题”，再回复 Bot 发出的指定消息；“已处理”和“稍后 1 小时”仅作用于本机。原生审批仍在原 Codex 客户端处理，稍后处理不会批准或解除原生等待。

在主对话或任意已授权的私聊话题发送 `@论文 检查最新批注`，或 `/to 论文 检查最新批注`。别名由桥接程序识别，不要求创建对应的 Telegram 用户。目标配置可增加 `"aliases": ["论文", "paper"]`；`/aliases` 只列出本机可用名称。别名重名时使用 `/to` 按钮选择具体会话。也可发送 `/to`，点击目标，再回复弹出的派单消息。回复只绑定该条指定消息，不会改变主对话原来的默认会话。

派单保存明确的本机原 thread ID 和话题 ID；恢复时不按别名重新选目标。目标绑定改变时会拒绝旧任务，不自动改投。回复保留在目标话题，并以正文汇总到本 Bot 的主对话；派单确认、按钮及回复提示也统一显示在主对话。派单目前支持文字，附件请直接发到对应话题。

本机队列自动运行，无需配置 SSH、汇总主机或 peers。外机别名、旧跨机按钮和直接注入的外机任务均会被拒绝；旧全局缓存不参与展示。升级时取消尚未投递的旧跨机任务；已经开始的原 Codex 任务继续由本机管理。历史记录保留，但不会继续跨机回传。旧的 `control_hub`、`control_hosts`、`control_peers` 配置不再启用任何跨机器能力，可删除。

## 附件与可靠性

Telegram 托管 Bot API 的附件下载上限为 20MB。图片作为 `localImage` 发送；其他文件下载到本机私有目录后提供文件元数据与本机路径。相册聚合后作为一次输入。

语音和视频目前按文件接收，没有自动转写或抽帧。生成文件暂不会自动上传回 Telegram。转接层不自动执行或解压附件，也不向模型暴露带 Token 的下载链接。

消息接收与 offset 原子提交。每条输入和回复保留自己的会话与话题，切换和重建入口不会把旧任务结果转发到另一个会话。Telegram 发信没有幂等键，因此发信成功但本地尚未提交时崩溃，仍可能重复投递一次回复。

删除话题后可使用 `/sessions` → 选择原会话 → **重新创建话题** → 确认，保留原 Codex 历史。旧话题的未送达回复会保留，不自动重发或重复执行任务。
